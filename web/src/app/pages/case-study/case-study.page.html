Case study

Document governance for construction projects

How DocRoof enforces document-control rules with Angular, ASP.NET Core and SQL Server, in the service layer and in the database.

All three planned phases are built and tested, and CI runs on GitHub. The hosted demo is not live yet (it needs the owner's accounts). Numbers come from docs/STATUS.md; source at github.com/ved-cmpt/DocRoof.

The problem

Drawings and specifications change for months. Site teams need the current revision, reviewers need to know which revision a question is about, and managers need to prove who approved what. In email and shared folders, superseded files get built from and approvals get lost.

DocRoof's scope is narrow on purpose: document governance — revisions, RFIs, submittals, decisions and audit. No scheduling, procurement or cost tracking.

Roles

Roles belong to a project membership, so one person can hold different roles per project.

Project roles
Role Responsibilities
Document Controller Uploads and versions records, coordinates submittals, accepts extracted metadata.
Project Manager Assigns reviewers, approves and closes RFIs, finalizes submittals.
Reviewer Answers assigned RFIs; one decision per submittal review cycle.
Requester Raises RFIs that cite a revision and page.

Business rules, enforced on the server

  • Document numbers are unique per project; revision labels unique per document.
  • Stored revisions never change: the service layer, an EF Core interceptor and a SQL trigger all reject edits.
  • Uploads must match an allowed type by their first bytes (PDF, TXT, PNG, JPG).
  • RFIs move Draft → Submitted → Assigned → Answered → Closed. Only the assignee answers; only a project manager approves and closes.
  • Citations stay pinned to the cited revision and page.
  • One submittal decision per cycle; Revise & Resubmit needs a newer revision.
  • Stale rowversions return 409; other tenants' IDs return 404.
  • Every change writes an append-only audit event in the same transaction.

Architecture

A modular monolith. Controllers delegate to services that own validation, authorization, transactions and audit; EF Core talks to SQL Server. In production the API also serves the Angular build, so the auth cookie stays first-party.

Data model

Schema, indexes and the documented vw_ReviewQueue view are in docs/DATABASE.md.

Security

  • Same-origin cookies (HttpOnly, Secure, SameSite=Strict) plus antiforgery on every unsafe request.
  • Object-level checks in services: tenant membership and project role on every call.
  • Upload hygiene: magic-byte allow-list, size limits, generated storage keys, active-content PDFs download-only.
  • Untrusted text: extraction can only create suggestions; a seeded prompt-injection PDF proves it in a test.
  • Abuse controls: rate limits, lockout, demo and upload quotas.
  • Headers: CSP, HSTS in production, frame-ancestors none, nosniff.

Deployment

The image, Render blueprint, Azure SQL Bicep template and smoke scripts are in the repository, and the image passes the smoke test locally. Hosted deployment: not complete.

Known limitations

  • No malware scanning of uploads; type sniffing and size limits only.
  • No OCR: image-only PDFs show “No text layer detected”.
  • Rules-based extraction targets title blocks like the seeded documents'.
  • PDF active-content detection is heuristic.
  • Notifications are in-app only.
