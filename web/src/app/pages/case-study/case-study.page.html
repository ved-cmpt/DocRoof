Case study

DocRoof: document governance for construction projects

An independent portfolio project exploring how a construction company's document control could be built with Angular, ASP.NET Core and SQL Server — with the business rules enforced where they belong: in the service layer and in the database.

The problem

On a building project, hundreds of drawings and specifications change over months. Site teams need the current revision; reviewers need to know which revision a question refers to; managers need to prove who approved what. When this lives in email threads and shared folders, superseded documents get built from, RFIs point at "the latest spec", and approvals are hard to trace.

DocRoof's scope is deliberately narrow — document governance: controlled documents and revisions, RFIs, submittals, review decisions, approval traceability and audit. It does not do field work orders, procurement, scheduling or cost analytics.

Users and roles

Roles belong to a project membership, not to a global account, so the same person can hold different roles on different projects.

Roles
Role (per project) Responsibilities
Document Controller Uploads, versions and distributes records; coordinates submittals; accepts extracted metadata.
Project Manager Assigns reviewers, approves RFI answers and closes RFIs, finalizes submittals.
Reviewer Answers assigned RFIs and records one decision per submittal review cycle.
Requester Raises RFIs that cite a revision and page, and sees responses.

Business rules, enforced on the server

  • Document numbers are unique per project; revision labels are unique per document.
  • A revision's content columns never change after insert: the service layer, an EF Core interceptor and a SQL trigger all reject it.
  • Uploads are accepted only when their first bytes match an allowed type (PDF, TXT, PNG, JPG) and the size limit; executables are rejected even when renamed.
  • RFIs follow Draft → Submitted → Assigned → Answered → Closed (Reopened → Assigned). Only the assignee answers; only a project manager approves and closes; a second approval returns 409.
  • RFIs cite a revision of the same project and a page within its page count; citations stay pinned.
  • Submittals allow one decision per review cycle by the assigned reviewer; Revise & Resubmit needs a newer revision and starts a new cycle.
  • Stale rowversions return 409, so concurrent edits never overwrite each other silently.
  • Another tenant's or project's IDs return 404, so existence is never leaked.
  • Every change writes an append-only audit event in the same transaction.
  • Extraction only proposes values with a cited page; a person accepts or rejects each one.

Architecture

A modular monolith: the Angular app calls the ASP.NET Core REST API, controllers delegate to services that enforce validation, authorization, transactions and audit, and EF Core talks to SQL Server. In production the API also serves the built Angular files, so the auth cookie stays first-party.

Why this stack fits an enterprise construction team

Construction companies commonly run Microsoft-centred estates: SQL Server for project and financial data, .NET services behind the firewall, and browser front-ends for field and office staff. DocRoof uses that stack with the patterns such a team would expect to maintain: typed REST contracts and ProblemDetails errors, migrations under version control, constraints and triggers in the database, a documented T-SQL view for reporting, and automated tests that run against a real SQL Server rather than an in-memory fake.

Security decisions

  • Same-origin cookies (HttpOnly, Secure, SameSite=Strict) plus antiforgery tokens on every unsafe request — no tokens in browser storage.
  • Object-level authorization in services: membership in the caller's tenant and the project role are checked on every call; frontend hiding is never relied on.
  • Upload hygiene: magic-byte allow-list, size limits, generated storage keys, sanitized names, PDFs with scripts or launch actions served download-only.
  • Untrusted text: document text is data only. Extraction can create suggestions and nothing else; the seeded prompt-injection PDF proves it in an automated test.
  • Abuse controls: rate limits on sign-in, demo creation, uploads and extraction; account lockout; per-address and global demo quotas; guest upload quotas.
  • Headers: CSP, HSTS in production, frame-ancestors none, nosniff, Referrer-Policy, Permissions-Policy.

Deployment design

The production image, Render blueprint, Azure SQL Bicep template and smoke scripts are in the repository; the image was built and smoke-tested locally with Docker Compose. Hosted deployment: not complete — it requires the owner's accounts.

Known limitations

  • No malware or antivirus scanning of uploads; content-type sniffing and size limits only.
  • No OCR: image-only PDFs show "No text layer detected — extraction unavailable".
  • Rules-based extraction understands title-block conventions like the seeded documents'; real-world layouts would need more rules or the optional language-model adapter.
  • Active-content detection in PDFs is heuristic; it is a safety net, not a sanitizer.
  • Notifications are in-app only; no email is sent.
  • The hosted demo is not deployed yet (owner accounts required).
